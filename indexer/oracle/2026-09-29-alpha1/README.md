# The alpha1 oracle (2026-09-29)

The port of stratagems off `ethereum-indexer*` onto `@etherfold/*` is correct only if the new fold answers the questions `web/` asks the same way the old one did, over the same history. This folder holds what the old one answered, and the script that asks the new one.

## The oracle: `old-snapshot.state.json.gz`

The state the old pipeline computed for alpha1, as it computed it: the file the old snapshot job (`wighawag/stratagems-snapshots`, which ran `pnpm indexer:index alpha1`, that is `ei -p ./dist/index.cjs ... -f ../web/static/indexed-states/alpha1`) published, gzipped and otherwise byte for byte.

|                                    |                                                                                                                                                                                                                   |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| source                             | `stratagems-snapshots` commit `8b59f3b40c5b7020aae868a500c96185b6ff4ce9` (2025-01-30), `snapshosts/alpha1/8453-kh0jgy-8b3313bcfbef95ebec1f226c09fbc948f38418201150466cbeff2c3082df81d8-state.json`                |
| sha256 of that file (uncompressed) | `e7ddb76dcb1edae5ceab79609f2038e0b2b79e99becbdebc0de4be0a9413d065`                                                                                                                                                |
| block                              | `lastToBlock` 25,726,865 (Base)                                                                                                                                                                                   |
| processor                          | `8b3313bcfbef95ebec1f226c09fbc948f38418201150466cbeff2c3082df81d8`, the version hash `indexer/` builds to at `3d5a0b3` (the commit this port starts from), checked by building it on 2026-09-29 before any change |
| history covered                    | complete: the last alpha1 log is at block 23,303,136 (etherfold's capture of the whole deployment, 31,332 logs), below the snapshot's block, and the game is discontinued                                         |

It is also independently confirmed: it equals, after normalising the bigint encoding, the golden state etherfold's stratagems conformance workload computed by driving the same JS processor over its own capture of alpha1 (`packages/conformance-workload-stratagems/fixtures/stratagems-alpha1.state.json`).

It cannot be regenerated by this repository any more (the JS-object processor path is gone), which is why the file is committed rather than recomputed.

## The questions `web/` asks

Every read of the state `web/` makes, found by walking every use of the old state object (`state`, `$state`, `rawState`) on 2026-09-29. `src/queries.ts` asks all of them in ONE GraphQL document, so every answer is read as of one block.

|     | question                                                                 | where `web/` asks it                                                                                                                | entity                                 |
| --- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| Q1  | every cell, with its nine fields                                         | `ViewState.ts` (the view of every cell, `tokensToCollect`, `neighbors`), `TerrainLayer.ts`, `Blockies.ts`, the contract tests' grid | `cell`                                 |
| Q2  | the owner of every cell                                                  | `ViewState.ts` (`currentPlayer`, `numLands`, `tokensToCollect`), `Blockies.ts`                                                      | `cellOwner`                            |
| Q3  | the commitment of the connected account                                  | `ViewState.ts` (`hasCommitmentToReveal`)                                                                                            | `commitment`, `where: {account: {eq}}` |
| Q4  | the placements of the last 7 revealed epochs, with who placed what where | `EventsView.svelte`                                                                                                                 | `placement` + its `players`            |
| Q5  | the reward state of every account, and the global rate                   | `ActualLeaderboardView.svelte`                                                                                                      | `sharedRate`, `globalRate`             |
| Q6  | the points the game logic accumulated per owner                          | `StratagemsContract` (in `ViewState.ts`)                                                                                            | `computedPoints`                       |
| Q7  | the fixed-rate reward state per account                                  | nothing in `web/` (the admin scripts in `contracts/`)                                                                               | `fixedRate`                            |

Two answers `web/` DERIVES from those are compared as well, because they are what a player sees: D1, the lands still alive per owner at an epoch (`numLands`), and D2, the cells a viewport around (0,0) draws. `web/` asks for every cell and draws the ones in view, so there is no viewport query (and no prefix-keyed entity to make one).

## The comparison: `compare.ts`

```sh
pnpm indexer:index alpha1                    # etherfold build ... --publish (history none, no seed)
pnpm --filter ./indexer compare:alpha1
```

It answers each question three ways and compares them after canonicalising (object keys sorted, arrays in order, bigints tagged):

- ORACLE: the old state, read with the old code's own walks.
- FOLD: `indexer/data/alpha1.db`, the database `etherfold build` wrote, through `etherfold serve`'s `/graphql`, with `web/`'s own documents.
- PUBLICATION: what `--publish` wrote into `web/static/indexed-states/alpha1`, installed the way the web worker installs it (`openAndBootstrap` into the IndexedDB store, on `fake-indexeddb`) and asked through the IndexedDB accessor the worker's GraphQL reads. This half also measures the rows-examined bound the web app's document needs.

Q3 is asked twice: once for every commitment, and once with the document `web/` sends (one account), for every account that owns a cell or holds a reward state, plus one that never played.

## Folding alpha1 without paying for it twice: `rpc-cache-proxy.ts`

Folding alpha1 means scanning Base from block 12,082,311 to the tip (51,900,000 and counting) for two addresses. `https://mainnet.base.org` answers `eth_getLogs` over at most 2,000 blocks, about five requests a second, so the scan is about 20,000 requests and an hour. The browser check (`web/verify/alpha1.spec.ts`) needs a tab that indexes alpha1 itself too. The proxy fetches each 2,000-block chunk once, caches it under `indexer/data/rpc-cache/` (git-ignored) and answers any range up to 200,000 blocks from the cache, so both folds read the same logs and the second one is fast. It changes no answer; every other method is passed through.

```sh
pnpm --filter ./indexer exec tsx oracle/2026-09-29-alpha1/rpc-cache-proxy.ts --upstream https://mainnet.base.org --port 18546
ETH_NODE_URI_alpha1=http://127.0.0.1:18546 LEARNED_RANGE='{"safeSpan":200000,"nextSize":200000}' pnpm indexer:index alpha1
```

### Rows examined

The IndexedDB accessor answers a list by scanning the entity's live rows and refuses past a bound (25,000 by default, etherfold ADR-0099). A root list with no prefix examines every live row of its entity, whatever its `where`; a nested list examines its parent's children. On alpha1 the web app's one document examines, per list: `cell` 1,956, `cellOwner` 1,956, `sharedRate` 34, `fixedRate` 34, `computedPoints` 33, `placement` 7 (+ 25 players under them), `commitment` 0 (it holds none at the end of the game), `globalRate` 1. The largest scan is 1,956 rows, measured above as the smallest bound the document passes, so nothing is near the bound and `web/` keeps the default.

## Result (2026-09-30, later): etherfold 0.11.0, then Hardhat 3

### etherfold 0.11.0 and `"sideEffects": false`

`etherfold@0.11.0` with `@etherfold/core@0.11.1`, `@etherfold/processor-entities@0.4.1` and `@etherfold/state-store@0.5.1` declare `"sideEffects": false`, so the bundle no longer carries etherfold's module-level loggers: it shrinks from 14.6 KB to 11.6 KB, holds no `@etherfold/` logger string, and its identity moved one last time, to `sha256:e4a5b95ba471698ba29e8fd624ffb3d224e0655d3661af9891f69c9120d8159d`. From now on an etherfold upgrade moves it only when code the bundle actually runs changes.

`pnpm indexer:index alpha1`, into an empty `data/alpha1.db` through the proxy, took 241 s and published generation `dbe71f606c80350a56819d13a51ba4ab` (cut 51,995,296, `takenAt` 23,303,136, body `state-cf1d9d12...ndjson.gz`). The CLI now says when a bundle is new to a publication directory:

```
new processor: sha256:e4a5b95b... is not among the processors .../publication.json held a snapshot of. [...]
  held: sha256:3a768a1a...
  held: sha256:6e22cab1...
```

The body's rows are again byte for byte those of every earlier publication. `compare:alpha1`: every question answered the same, both reads name `takenAt` by hash, rows examined 1,956 at most; `--negative-control` still fails (Q1 DIFFERENT, exit 1).

Real Chromium, `web/verify/alpha1.spec.ts`, 2 passed (39.6 min): from the publication 17 s, indexing itself 2,315 s, the election 30 s (writer) and 5 s (reader).

### Hardhat 3, hardhat-deploy 2, rocketh 0.23

etherfold refuses a log that carries no `blockTimestamp`, which only EDR >= 0.20 (Hardhat >= 3.17) supplies, so `contracts/` moved to Hardhat 3. rocketh 0.19+ exports the chain as `chain: {id, genesisHash, ...}` instead of `chainId` / `genesisHash` / `chainInfo`; `indexingSource` builds the same source from it, checked byte for byte against the old export for alpha1, so the stream digest (`c4d140b82c4f004d824c59fb46188361`) and the publication above are unchanged.

Real Chromium on that build, 2 passed (38.3 min): from the publication 14 s, indexing itself 2,242 s, the election 28 s (writer) and 5 s (reader). The same state as of block 23,303,136 (`0x36c9b72d...`) every time, the oracle's.
